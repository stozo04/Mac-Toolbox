# Vault

**Page:** top-level, the **Vault** pill next to AI Models (`Page.vault`)
**Code:** `Sources/Toolbox/Vault/`

A password-protected, hidden place for photos and videos. Toolbox is the friendly way in (a bank vault door you unlock), but the files are protected without Toolbox too: they live in an AES-256 encrypted disk image that Finder only opens with the same password.

## Design reference
No screenshot in `images/`. The door is design A (round bank vault door with a spoked wheel) picked in the planning conversation: the wheel turns, then the door swings open on its left hinge and the library fades in.

## Current state
Built: storage, lock screen, move in, delete, viewer, browsing by kind and length, duplicate grooming, and smart search (EmbeddingGemma 2 on llama.cpp, on device).

- `VaultDoor` - the one owner of the encrypted image: every create, unlock, lock, eject and password change runs through it, one at a time, and it is the only code that runs `diskutil` or `hdiutil` for the vault (through `Shell.run`; `VaultTool` is the seam the tests replace). `diskutil image create blank --encrypt` (AES-256 APFS sparse bundle, 2 TB cap, only uses what is stored), `diskutil image attach --nobrowse` to a hidden mount point, `diskutil eject` (then `hdiutil detach -force`) to lock, `diskutil image chpass` to change the password. The password goes in through standard input, never as an argument, and is never stored or logged. No `sudo`. It is a class with lock-guarded state and a chain of operations, not an actor: an actor lets a second call in at every `await`, and sleep needs an answer it can wait on without the main actor.
  - State is held, never worked out afterwards from what is mounted: `closed`, `mounting`, `open` (by this copy), `closing`, `openElsewhere`. Every operation answers with an outcome: an unlock is `opened`, `lockedMeanwhile` or `refused(why)`; a lock is `locked`, `stillMounted(reason)` or `notOurs`.
  - A lock voids the unlocks waiting their turn and cancels the attach of the one that is mounting. That unlock ends without ejecting anything; the lock is next in line and does the one eject, so the attach process is gone before the eject starts and two ejects never run at once.
  - Time limits: attach 60 s; eject 6 s, then forced detach 6 s; a program past its limit is stopped and killed 2 s later. A lock therefore ends within 18 s of starting (2 s for an attach it interrupts, then 8 s for each step), whatever the tools do. Not counted: up to 5 s per output pipe that `Shell` waits when a tool exits but a child of it keeps the pipe open.
  - Creating the image and changing its password run `.untilFinished`: no timer, cancel or quit ever stops them, because a write cut off halfway could damage the vault. A lock asked for during a creation answers at once (nothing is mounted); one asked for during a password change of an open vault waits its turn behind it, so sleep or quit can reach their bound with the vault still mounted in that case. The door says which write is running (`unfinishedWrite`), so quit and sleep's log can name it.
  - Across copies of the app, ownership is a lock file beside the image (`Vault.lock`, holding the pid and start time for diagnostics), taken with `flock` before anything is attached and held while this copy has the vault open. `flock` belongs to the open file, so a copy that crashes gives it up without anyone noticing, and the next copy takes it over. A copy that cannot take it runs no tool, never ejects, and its door says "The vault is open in another copy of Toolbox. Lock it there first."; two copies unlocking at the same instant are decided by who gets the lock. Versions before 0.11.9 take no lock file, so a mount this copy did not make is also left alone while another copy of the app is running; with no other copy running it is a crash leftover and is ejected at launch or before the next unlock. A leftover that will not eject at launch is kept as this copy's open vault: the door says it may still be readable in Finder, unlocking retries the eject, and quitting is refused once. The cost: a mount left by a crash is not recovered while a second copy is running, even an idle one; quit the other copy, or eject the volume, and unlock again. Once no copy older than 0.11.9 can be running, delete this check: the `anotherCopyIsRunning` parameter of `VaultDoor` and `VaultModel` (default `VaultDoor.anotherCopyOfThisAppIsRunning`) and its three guards, in `clearTheWay`, `undoMount` and `closeLeftover`; the lock file alone then decides.
  - Unlocking refuses to mount over a mount-point folder that already holds files (anything but `.DS_Store` or the Spotlight marker): they would be hidden while the vault is open and still unencrypted afterwards, so the door names the folder, says to move them somewhere else and offers to show the folder in Finder. A mount that fails (a wrong password, a timeout, a tool that cannot start) is closed again and its empty folder removed.
  - The image is created under a temporary name beside it (`.Vault-<uuid>.sparsebundle`) and moved into place only when the tool succeeded, with a move that fails if a vault is already there (`renamex_np` with `RENAME_EXCL`), so create never deletes or replaces the real image; a failed creation removes only its own temporary image, and one left by a crash is ignored and removed by a later create once it is over an hour old.
- `VaultDisk` - what is on disk for the vault and what can be read without running a program: where the image and mount point are, whether the image exists, whether the volume is mounted.
- `VaultLocation` - `~/Library/Application Support/Toolbox/.vault.noindex/Vault.sparsebundle`, mounted at `.../.vault.noindex/Open.noindex`. The folder is a dot folder with Finder's hidden flag set. Only the installed app uses it: a development run (a debug build, or anything run from `.build/`) gets `.../Toolbox/.vault-dev.noindex` from `VaultLocation.launch`, so it never opens the owner's vault.
- `VaultMover` - moves files in: copy, check size + SHA-256 + that it opens, flush the copy to the disk (`F_FULLFSYNC`), check the copy is on the mounted vault volume (not in the plain mount-point folder of a vault that was detached meanwhile), then delete the original for good. Any failure keeps the original and removes the copy. Refuses non-media, files inside a `.photoslibrary`, iCloud files that are not downloaded, and files already in the vault. Folders expand to the photos and videos inside them. Name clashes become "name 2.ext".
- `VaultLibrary` / `VaultItem` - lists photos and videos in the vault (newest added first), skipping hidden files, so `.toolbox/` and `.metadata_never_index` never show.
- `VaultThumbnails` - Toolbox makes its own thumbnails (ImageIO, AVFoundation) and keeps them inside the vault in `.toolbox/thumbs`, so macOS never caches previews of vault files outside it. In memory it holds the most recently shown ones, up to 64 MB of pixels, and a tile that scrolled away before its turn is not decoded.
- `VaultModel` - phases setup / locked / opening / open; it mirrors the door and never ejects anything itself. Lock, leaving the Vault page and screen lock show the door at once and the eject finishes in the background; unlock and create are refused until it has settled. If the vault will not eject, the library comes back with the reason. If an unlock fails after macOS mounted the volume and neither the eject nor the forced detach removes it, the door stays shown with a notice that the vault may still be readable in Finder, and quitting is refused once, as for any mounted vault. Sleep does not return until the door has locked the vault or its 18 s bound has passed; it waits on the door's own answer from the main thread, and nothing on that path needs the main actor (closing the search index first can take up to 3 s more). Quit goes through `QuitPreparation` (`applicationShouldTerminate` answers `.terminateLater`) and `VaultQuitGuard`: it waits up to 20 s for the lock; if the vault is still mounted, or a creation or password change is still running, the quit is cancelled, Toolbox comes forward on the Vault page and says why, what to do, and that quitting again quits anyway. For a mounted vault that means it stays open until it is ejected or the Mac restarts; for a creation it means creating the vault again, because the finished image is only moved into place by the app; for a password change the change still finishes. The notice is removed once what it waited for is done. Only then does `Shell` stop what is still running, and it stops only `.untilCancelled` programs, which the vault never uses; a creation or password change still running is left to finish on its own. A vault found mounted at launch is locked unless a running copy holds it. If the vault is ejected from outside the app while it is open, the model notices and goes to the locked state without running any disk tool: before and after each batch moved in, when the search index or a search fails, when the app becomes active, and when macOS reports the vault's volume unmounted (`lockIfClosedFromOutside`). The door then says the vault was closed from outside Toolbox and to unlock to continue. The report of a batch that was running is checked against the disk, because a move deletes the original for good: a file is listed as not moved, still where it was, only if its original still exists; a file whose original is already gone (its move finished just as the vault closed, including one that finishes after the notice) is listed separately as "finished moving just as the vault closed; check it after you unlock", and the door notice counts those. A missing vault is never shown as a search problem. Files moved in appear in the grid one by one, and the library is read in full once per batch.
- `VaultDoorView`, `VaultLibraryView`, `VaultViewer` - the door, the grid (Select, ⌘/⇧-click, Delete key, context menu, drag-and-drop, Add, video tiles show their length), and the viewer (← / → buttons and arrow keys follow what the grid shows, Esc, videos play inline from the start).
- `VaultBrowse` - the All / Images / Videos filter (each tab shows its count, and the header's "N items, size" follows the chosen tab) and, under Videos, sorting by length (shortest or longest first; videos whose length can't be read go last). Lengths are read with AVFoundation in the background each time the vault opens and kept in memory only. During a search the filter still applies but the order stays the search ranking.
- `VaultDuplicates` - the one matcher, used by an add and by the View menu's **Duplicates**. It lists pairs of the same photo or video, marked **Exact** or **Likely**, and joins pairs that share a file into sets. Exact: the same bytes (same size first, then SHA-256; names don't matter). Likely: two videos whose names carry the same post ID (the last `[…]` holding a 15-20 digit TikTok/X ID or an 11-character YouTube ID, else a bare 15-20 digit number as in `tiktok_7468015357786148128`; tags like `[Official]`, dates and ssstik's 13-digit download timestamps don't count) and whose lengths are within 2 s, or two files that look the same: `VaultLook` (in `VaultLook.swift`) keeps a 256-bit difference hash of each photo and of video frames at 0.25, 1, 2.5, 4, 6 and 8 s (those inside the clip); videos within 1.5 s of each other compare only frames taken at the same moment and match when each is within 40 bits (24 when they share a single frame), photos when they're within 24 bits and have the same shape. Only videos with another video of nearly the same length are read; for an add, only vault videos near an incoming video's length, and only vault files the size of an incoming file are hashed. Lengths are read before matching, because a missing length lets a post ID match on its own. On the 415-file vault the thresholds were checked against: true pairs scored at most 39 bits, different videos at least 72, different photos at least 43. `VaultMatchCache` keeps each file's hash and look while the vault is open, so an add and the Duplicates view read a file once.
- Adding (`VaultModelAdding.swift`) checks the incoming files against the vault before anything moves ("Checking the new files…"). Files with no copy go in as before; then each set that holds an incoming file opens the comparison screen, with every copy in it: all its vault copies and any other file of the same add it matches. Nothing is ticked: you tick the copies to keep. A vault copy left unticked goes to the vault's Trash; an incoming file left unticked stays exactly where it was, untouched, because nothing ran on it; a ticked one moves in with the usual verified move under its own name. Every copy is checked again just before the choice is carried out, and a set whose files changed is left alone. Ticking every copy keeps them all and remembers the set (below), so it is never suggested again. Cancel or Esc stops the add; files not reached stay where they were and are not reported as failed (`VaultMoveTracker` sets them aside). The add ends with "N added, N replaced with a better copy, N kept as they were, N kept both", a neutral note that clears when the vault locks. Lock, sleep, quit or an outside eject end the review like any move.
- `VaultComparison` / `VaultComparisonView` - the comparison screen, one screen for an add, the Duplicates view (**Compare…** on a set, **Review All**) and Download Video's matches. Header "These files look like the same video/photo" with an Exact or Likely badge; one pane per copy, up to three side by side, more in one row that scrolls sideways so their lines stay level. Each pane has a **Keep** box and says where the copy is ("Already in the Vault", "Adding now", "Added by Download Video", or the date added and "Oldest" in the Duplicates view). Videos (`VaultSyncedPlayback`): **Play** plays the selected copy alone, and selecting another carries on from the same moment; **Play All** plays every copy together on one clock with the sound of the copy whose speaker is on; one scrubber moves them all. Photos (`VaultZoomGroup`): shown at the same size; click and hold zooms every photo to the same spot. Keys: ←/→ select a copy, Return ticks it, ⌘Return confirms, Space plays, Esc cancels. "Do the same for the remaining Exact matches" repeats a choice of one side (vault copies only, new files only, oldest, newest) or of all copies on every later exact set of that add or review; it is never remembered.
- `VaultQuality` - each copy's readout, read with Media Info's `MediaInspector` and ImageIO (also behind Details): resolution with a label by the short side (4K, 1440p, 1080p, 720p, 576p, 480p), frame rate, codec, bit depth, dynamic range, color, overall and video bitrate, sound, audio bitrate, sample rate, channels, length, container, recording date, location, metadata, size, name and dates; for photos dimensions, format, bit depth, color profile, HDR gain map, camera, lens and date taken. Lines that differ are bold; a green mark sits on each line where more is plainly better (resolution, bitrates, frame rate, bit depth, HDR, sound). **Higher quality** goes to the copy with more pixels, then higher overall bitrate (within 2% is equal), then frame rate (within 0.05 fps); photos with equal pixels read "Same quality".
- `VaultDistinctPairs` - `.toolbox/duplicates.sqlite` inside the encrypted image: `distinct_pairs` (every pair of different files in a set kept whole, by their SHA-256, so renames keep it), `kept_copies` (identical files share one digest, so for them it keeps how many were kept; one copy more is suggested again) and `pending_reviews` (downloads to compare, below; a review cancelled part-way leaves the downloads it didn't reach queued). Not `index.sqlite`, which a new search model empties. A file that won't open is logged and the choice simply isn't remembered.
- `VaultTrash` - the vault's own Trash, `.toolbox/trash/` inside the encrypted image: where copies not kept on the comparison screen go. The library shows it with Put Back All (back under their names, "name 2" when the name is taken) and Empty Trash (permanent, after a confirmation). macOS's Trash is not used: for the hidden `--nobrowse` vault volume it either keeps files where Finder can't reach them (`.Trashes` on the volume) or would show them, with previews, outside the vault.
- `VaultDetails` / `VaultDetailsSheet` - **Details…** (right-click under Delete, or ⌘I and the ⓘ button in the viewer): kind and the `VaultQuality` readout (MP3 sound hidden from AVFoundation is reported from the playable copy). Rename edits the name, never the extension, and refuses empty names, `/` or `:`, a leading dot, over 255 bytes or a name another file has; a case-only rename goes through a temporary name. The file's search entry (`VaultIndex.rename`), thumbnail and playable-copy records move with it, so nothing is re-embedded. Smart search status is read from the index (`coverage`, ignored when the file's size or date changed): in search (picture and/or sound), being added, not in search (Add to Search), couldn't be read (Try Again), or the model isn't downloaded. Add to Search moves the file to the front of the indexing queue.
- `VaultPlayable` - some videos (HEVC with MP3 sound in an .mp4, common in TikTok downloads) have sound AVFoundation can't see, so they played silently and their sound wasn't searchable. When AVFoundation finds no sound track but ffprobe finds one, ffmpeg makes a lossless `.mov` copy (streams copied, not re-encoded) in `.toolbox/playable/`, inside the encrypted image. The viewer plays it and search reads its sound; the vault file itself is never changed. Each video is looked at once: `<key>.checked` (no copy needed) or `<key>.failed` (logged with `VaultLog.failure`) is kept beside the copies, so silent videos aren't probed again and a failed copy isn't retried until the file changes. Videos indexed before this have their sound read once more. Cancelling (leaving the viewer, locking) is never recorded as a result. Unfinished copies are removed when the vault opens; copies of removed videos are pruned. ffmpeg/ffprobe are the ones bundled in Toolbox.app (`MediaTools`).
- Smart search (`Search/`):
  - `VaultSearch` target (`Sources/VaultSearch/`, adapted from DigUp, MIT, see `LICENSE-DigUp`): `LlamaEmbedder` runs EmbeddingGemma 2 through llama.cpp (`Sources/CLlama`, built by `scripts/build-llama.sh` at DigUp's tag and patch) on the GPU; `MediaPieces` turns a photo into a 1024 px JPEG, a video into a frame every 3 s (one per shot) and 30 s sound windows; `Scoring` compares a query with every vector and centres each kind (image, audio) on its own average; `EmbeddingModel` finds the model files (Toolbox's own folder, DigUp's, the Hugging Face cache) by exact size.
  - `VaultSearchEngine` runs it all on one background queue. Every file it writes (the work JPEGs and WAVs, the index) is inside the mounted vault in `.toolbox/`, and it refuses to open anything when the vault isn't mounted. Locking closes it first (3 s at most).
  - `VaultIndex` is `.toolbox/index.sqlite`: one 768-float vector per photo, video frame and sound window, plus each file's size and modified date so changed files are read again. It records which model made its vectors; a different model empties it.
  - `VaultRanking`: "Best matches" are files whose best meaning score is 2 standard deviations above the rest (DigUp's rule) or whose name holds every search word. "Might also match" adds files half a deviation or more above the average: a vault is full of similar photos, and when a third of them show a phone, none of them stands out by 2 deviations. With neither, the 6 nearest show as "No close matches". Videos found by search still open from the start.
  - `VaultModelDownload` downloads the two model files (865 MB) from Hugging Face when neither DigUp nor an earlier download has them, and checks their SHA-256 before keeping them.
  - Indexing starts when the vault opens and after files move in; the full model (about 1 GB) is freed when it finishes, and searches use the text half (about 0.3 GB).
- Tests: `VaultBrowseTests.swift`, `VaultDetailsTests.swift` (rename rules, search entry following a rename, details of a real clip and photo), `VaultDuplicatesTests.swift`, `VaultLikelyDuplicatesTests.swift` (post IDs, look matching, two real encodes of one video), `VaultMatchCacheTests.swift` (what an add reads, sets kept whole), `VaultQualityTests.swift` (labels, ranking, two real encodes), `VaultComparisonTests.swift` (nothing ticked, the repeat box, cancel), `VaultAddDuplicatesTests.swift` (an add on a real encrypted image: keep either side, keep all, cancel, a changed copy, lock mid-review, a queued download), `VaultPlayableTests.swift` (with an HEVC + MP3 fixture; needs ffmpeg, which CI builds with `scripts/fetch-tools.sh`), `VaultTests.swift`, including a real encrypted image (create, wrong password refused, move in, lock, change password, old password refused); `VaultSearchTests.swift`, including a real-model search (skipped when the model isn't on the Mac, as on CI).

- Download Video's "Add to Vault" opens the vault with Touch ID (`openWithTouchID` in `Tools/Video/DownloadVideo/DownloadVault.swift`), leaves a download in Downloads (and sends it from there) when the vault already holds the same bytes (`holdsExactCopy`: sizes, then a hash only on a size clash), moves the others in with `VaultModel.moveIn` (one file, awaited, refused with `VaultMoveError.busy` while a drop is moving files in) and queues each for a duplicate check (`queueDuplicateCheck`); the next time the Vault page opens normally it compares them in the background and, if any matches, offers **Compare…** for them, where an unticked downloaded copy goes to the vault's Trash, puts them all in line for the index together and waits for each (`makeSearchable` in `DownloadVault.swift`, over `VaultModel.makeSearchable` for one file: first in line, answered once it is indexed, could not be, or the vault locked; queued together so one pass takes them all and the search model is loaded once, with one shared deadline of `searchWaitLimit` per file; the waits live in `Vault/Search/VaultSearchWaiters.swift`, which answers each exactly once, by the index, its time limit or search stopping, and follows a rename), and locks again with `lockAndConfirm`. The password is saved for this only when "Use Touch ID to add downloads" is ticked on the door at unlock or create, and forgotten the moment it is unticked. `VaultTouchIDKey` seals it with a Secure Enclave key that needs the current fingerprints (`.biometryCurrentSet`), in `TouchID.key` beside the image (mode 600, never logged). The Keychain is not used because the app is ad-hoc signed, and macOS would ask for the login password after every rebuild. A wrong saved password drops the file, and so do changed fingerprints (the file keeps the Touch ID domain state from when it was saved, so a passing error never drops it). A save that fails drops the old file too. The file is written with mode 600 from the start and renamed into place. `VaultLog` drops the vault path from `VaultMoveError.originalKept` before logging. A password change updates it. `openQuietly` opens with that password without leaving a message or attempt count on the door.

## Rules for this page
- Moving in deletes the original. This is a deliberate exception to "never modify original user files" (see AGENTS.md).
- Delete inside the vault is permanent (no Trash), after a confirmation. Copies not kept on the comparison screen go to the vault's own Trash (`VaultTrash`) instead, inside the encrypted image, until you put them back or empty it. A new file not kept is never touched.
- Vault logs never carry file names: `VaultLog` keeps the extension and size only and scrubs the name out of error text.
- Spotlight: nothing is indexed on the mounted volume (nobrowse mount, `.noindex` path, `.metadata_never_index`). DigUp skips it too: its crawler ignores hidden folders, packages and `.noindex` folders.
- Network: only the one-time model download from huggingface.co, when you press Download. Nothing from the vault is ever sent; search runs on this Mac.
- Apple silicon only: llama.cpp is built for arm64, and so is the app.

## Debugging
```
.build/debug/Toolbox --page Vault --vault-folder /tmp/vault-test
```
Debug builds only (all three are compiled out of release builds): `--vault-folder <folder>` puts a test vault anywhere instead of the development folder, `--vault-debug-password <pw>` pre-fills the password fields and `--vault-debug-add <folder>` moves that folder's photos and videos in once the door opens.
